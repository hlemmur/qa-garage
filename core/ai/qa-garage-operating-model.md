# QA Garage Operating Model

The QA Garage is a thin harness layer over a library of vendored QA skills (`.agents/skills/`). AI agents act as supervised QA operators; the human QA Lead owns priority, expected behavior, risk acceptance, and final approval. This document defines how agents orchestrate the skills, where artifacts live, which "hat" applies, and what requires approval.

## Path & Project Conventions

- Each target under test is its own QA root: `projects/<project>/`.
- The single source of truth is `projects/<project>/.agents/qa-project-context.md`. Every vendored skill reads it first and must not duplicate it.
- Targets are **black-box**: skip the skills' codebase-detection steps and source facts from documentation and exploration instead. Record what is true or observed, never invented.
- **Reference layer:** `reference/` — features, use cases, product map, glossary, testability (living product knowledge).
- **Skill-owned artifacts:** `risk-matrix.md`, `journeys/`, `strategy.md`, `plan.md`, `test-data.md`.
- **Test design:** `scenarios/` — testable specs; approved scenarios become assertion ground truth.
- **Client scope:** `proposals/` — synthesized scope documents for stakeholders.
- **Operations:** `jobs/`, `cadence.md` — scheduled work instances and per-project cadence.
- **Human-decides loop:** `decisions.md`, `questions.md`, `known-issues.md`. `open-items.md` is generated by `qa:review`.
- Vendored `SKILL.md` bodies stay pristine (updatable via `skills-lock.json`). Adapt through this model and conventions, never by editing skills.

## Operating Loop

1. Read `qa-project-context.md`, `reference/`, `plan.md`, relevant `journeys/`, `risk-matrix.md`, and scenario files.
2. Check the readiness gate: run `QA_PROJECT=<project> npm run qa:review -- --gate`. If blocking items exist, do not start **execution** work unless `decisions.md` records an override. Discovery and reference updates are not blocked.
3. Pick the role-hat and skill for the task (see routing table).
4. Run deterministic checks before exploratory work when practical.
5. Collect evidence for every suspected issue.
6. Separate observations, hypotheses, and confirmed failures.
7. Record findings in the right artifact (reference, known-issues, questions, risk updates) with source and evidence.
8. Draft reports, regression candidates, or scope proposals for human review.
9. Update confirmed expected behavior, `qa-project-context.md`, or scenarios only after the human accepts the change in testing intent.
10. Run harness `knowledge-curator` — mandatory reference and artifact updates (see `knowledge-maintenance.md`).
11. Regenerate `open-items.md` (`qa:review`) and end with an ACTION REQUIRED summary if anything awaits a human.

## Role-Hats

One agent adopts one hat per task. Hats map to collaboration channels and future runtimes (cron executor vs on-demand architect).

- **Harness Maintainer** — edits `core/`, `scripts/`, adapters. Must not edit vendored skill bodies or project expected behavior.
- **Test Architect** — owns context, `reference/`, journeys, risk, strategy, plan, proposals, decisions, questions. Proposes scope and expected behavior; humans confirm.
- **Executor** — runs approved jobs and suites, drives browser (Playwright MCP), captures evidence. Respects execution gate. Proposes `observed` reference updates only.
- **Analyst / Reporter** — summarizes results, drafts bug reports, updates `known-issues.md`, `reports/`, `open-items.md`. Must not mark human review approved or hide failures.

**Collaboration:** QA Lead ↔ agent in Cursor chat → proposes jobs in `jobs/`/`cadence.md` → human approves → executor runs.

## Approval Gates

Ask for human approval before:

- Changing assertions or expected behavior.
- Promoting observed/inferred knowledge to `confirmed` in `reference/` or `qa-project-context.md`.
- Sending `proposals/` to a client.
- Marking tests skipped, flaky, or lower priority; deleting tests or scenarios.
- Updating visual baselines.
- Filing externally visible bug reports.
- Running destructive product actions.

### Discovery Gate (soft)

Phase 0 discovery and reference updates are **not** blocked by open access questions. Record blockers in `questions.md` and discovery reports.

### Execution Gate (readiness)

Do not begin execution-gated work (smoke/regression authoring, release-gating runs) while blocking items exist in `open-items.md`, unless `decisions.md` sets `Allow proceed with open questions: yes`. Enforced by `qa:review -- --gate`.

## Required Failure Classification

Classify every failure before proposing a fix:

- **Product bug** — behavior appears wrong against stated expected behavior.
- **Test bug** — automation is stale, flaky, or asserts the wrong thing.
- **Environment issue** — target, account, network, data, flag, or browser blocked the run.
- **Unknown** — evidence incomplete; more reproduction needed.

## Evidence Standard

A useful report includes: target URL and environment; account/role used (no secrets); steps attempted; expected vs actual; evidence paths; reproduction confidence; proposed artifact updates; suggested next action.

## Tooling Rules

Prefer CLI commands, Markdown artifacts, and Playwright output over tool-specific memories. Key commands:

```bash
npm run qa:knowledge    # validate context + reference/
npm run qa:review       # aggregate open-items (-- --gate for execution gate)
npm run qa:discover     # scaffold exploration session + job
npm run qa:proposal     # scaffold client scope proposal
npm run qa:tasks        # validate task ledger
```

Use vendored skills for craft; use this model for orchestration and guardrails. If an adapter conflicts, follow `core/ai/qa-principles.md` and this file first.
