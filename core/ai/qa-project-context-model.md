# QA Project Context Model

How durable product understanding is captured and governed. Replaces the old multi-file knowledge base with a single source of truth plus a few skill-owned artifacts, so there is no duplication and every fact has one home.

## Single Source Of Truth

`projects/<project>/.agents/qa-project-context.md` is read first by every vendored skill. It holds the nine sections: Product (incl. key user flows), Tech Stack, Test Stack, CI/CD, Environments, Quality Goals, Risk Areas, Team, Conventions. It is created and maintained with the `qa-project-context` skill.

## Skill-Owned Artifacts

Each concern has exactly one owner - this is what prevents the journeys-vs-features and mixed-risk overlaps of the old model:

| Artifact | Owner skill | Holds |
|----------|-------------|-------|
| `journeys/*.md` | `journey-mapping` | Real end-to-end user journeys (phases, touchpoints, emotions, pain points) - not feature lists |
| `risk-matrix.md` | `risk-based-testing` | Product/delivery risk scored Impact x Likelihood; no-go risks |
| `strategy.md` | `test-strategy` | How the project approaches quality; phasing |
| `plan.md` | `test-planning` | Current-phase coverage map |
| `test-data.md` | `test-data-management` | Accounts/data matrix (concurrency, permissions, invitations) |
| `reference/` | `project-discovery`, `knowledge-curator` | Features, use cases, product map, glossary, testability, ui-inventory (inline provenance) |
| `scenarios/` | harness + `playwright-automation` | Testable specs; approved scenarios become assertion ground truth |
| `proposals/` | `scope-proposal` | Client-facing scope documents synthesized from project artifacts |
| `jobs/`, `cadence.md` | harness `qa-cadence` | Scheduled job instances and per-project cadence overrides |
| `.agents/qa-project-context.md` | `qa-project-context` | Everything else (product, stack, integrations, environments, goals, team, conventions) |

Expected behavior is expressed through `strategy.md`, `plan.md`, approved scenarios, confirmed entries in `reference/`, and confirmed entries in `qa-project-context.md` - never in a separate overlapping file.

## Status & Provenance

When recording a fact, mark its confidence and source inline:

- `confirmed` - approved by a human or an authoritative source.
- `observed` - seen during exploration or a test run.
- `inferred` - reasoned from UI, docs, or behavior.
- `unknown` - explicitly unresolved (raise in `questions.md`).
- `outdated` - suspected stale; needs re-verification.

Always cite the source (human, docs URL, trace, screenshot, report, session log) and the date.

## The Human-Decides Loop

- `questions.md` - open questions; each flagged blocking or non-blocking.
- `decisions.md` - confirmed decisions and explicit overrides.
- `known-issues.md` - confirmed/suspected product issues with evidence.
- `open-items.md` - generated by `qa:review`, aggregating everything awaiting a human.

## AI Permissions

AI may add `observed`, `inferred`, and `unknown` facts with evidence, raise questions, propose risk and journey updates, and draft expected behavior.

AI must not, without human approval: promote `observed`/`inferred` to `confirmed` expected behavior, rewrite decisions, delete entries, mark expected behavior obsolete, or use unapproved knowledge as deterministic test truth.

## Contradiction Handling

When new evidence conflicts with an existing entry, do not overwrite it. Record the conflict, mark the old entry `outdated`, raise a question, and let the human resolve which is truth.

## Validation

`QA_PROJECT=<project> npm run qa:knowledge` checks that `.agents/qa-project-context.md` exists, contains the nine required sections, (for real projects) has no unfilled `[placeholders]`, and that `reference/` contains the five required files (`features.md`, `use-cases.md`, `product-map.md`, `glossary.md`, `testability.md`). `ui-inventory.md` is recommended after Phase 0B (warning if session logs exist but inventory is empty).
